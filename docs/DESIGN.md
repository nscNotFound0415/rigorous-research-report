# 设计说明

本文记录这套流水线的**结构决策**与**踩过的坑**。后者是主要价值：每一条都是「症状 → 为什么会发生 → 流水线用哪道机制挡住」，可直接对照检查自己项目的现状。

---

## 一、三条承重结构

### 1. 一个结构循环，复用在三个产物边界

调研报告的错误会级联：底表错 → 大纲错 → 全文错，而且越往后越难发现。所以复核不能放在最后做一次，必须**在每个产物边界各做一次**，且用**同一个**循环：

```
产出 → 独立审（异族模型、只读、附覆盖声明）→ 四档分流 → 修订 → 四层回读复验 → 出口
```

三个边界：**数据底表**（查口径、数值、证据锚定）／**章节大纲**（查覆盖、依赖、逻辑）／**合稿全文**（查一致性、痕迹、引用）。

出口条件是硬的：`D0=0` 且四层回读全过 且人放行。缺独立复核记录时该边界只能标 `BLOCKED_NO_REVIEWER`，**不得用规则扫描通过替代**。

### 2. 判实锤只走两条路

「已证实错误」必须有可复现的判定路径，且只有两条：**一手原文比对**（引用与原文 chunk 逐字比）/**纯算术复算**（代码执行）。任何需要「理解上下文才能判断」的东西，**降级为 D1（证据不足）或 D3（待核）**，交人裁决。

这一条是纪律的根：它让「能不能算实锤」变成机器可判定的问题，也让「定性裁决权归人类」有了明确边界——机器只处理能被两条路判定的，人处理其余。

### 3. 治理三件 + 四道门

- `brief.md` —— 项目背景**唯一事实源**（其余文件由它派生，内嵌项目宪法五原则）
- `progress-log.md` —— 进度与决策合一台账（四分状态：材料存在 ≠ 已复核 ≠ 已同步 ≠ 已审定）
- `change-table.md` —— 变更与指示处置对照表（回路载体）

四道人审门：**G0** 澄清定稿 → **G1** 大纲放行 → **G2** 纠错定性裁决 → **G3** 交付放行。

门禁的实现细节值得单列，因为它是「人审」能不能落地的关键：
- 签署件绑定被放行工物的 `sha256`，杜绝事后搭便车；
- `signed_by` / `authorized_by` 命中机器标记词表即拒（`agent`/`ai`/`bot`/`模型`/`自动`/…），且不误伤 `operator_huang`、`human:reviewer_lead` 这类人类标识；
- 含 `stub: true` 的签署件一律拒（`STUB_REJECTED`）——**演练桩不是人类签字**；
- 台账复选框的 `[x]` 只允许人类写，agent 写入一律被检出并回滚，记 `violations.log`。

**裁决归属与记录方式的分离**：门禁的裁决（APPROVED / REJECTED / CHANGES_REQUESTED）永远由人类作出，机器不得代为拍板。但「谁敲下这份文件」不再等同于「谁做的裁决」——人类在对话里说「通过」之后，Agent 可以用 `gate_guard.py --record-approval` 依授权原话代写签署件，代价是必须留下五个可回对的溯源字段（授权原话、会话与消息引用、授权时间、人类授权人、代录者），且 `authorized_by` 必须与 `signed_by` 同为人类身份。缺一即 `AUTHORIZATION_TRACE_INCOMPLETE` 阻断。

## 二、踩过的坑（按层）

### A. 事实与数据层

| 症状 | 为什么会发生 | 防线 |
|---|---|---|
| 百分比方向写反（「贵 78%」实为「便宜 78%」） | 同一句里分母换了却没换措辞 | 纯代码复算；正文里百分比必须带对照对象 |
| 毛利分母混用（收入分母与成本分母混在一句） | 同一指标在不同来源用了不同分母 | 底表每格声明 `expected_expression` 与 `tolerance` |
| 跨口径相减（自建成本 − 采购价） | 两套口径数字长得像就能加减 | 底表三口径分栏，`caliber` 不一致直接报错 |
| 无一手出处的自增数字（「50–70% 毛利」） | 上一轮的推算经一次转述获得了「历史依据」的身份 | 每个数值必须 `source_ref` 回指证据索引；无出处不入表 |
| 挂牌价被写成可采购价 | 官网展示价与下单页的差别被忽略 | 证据类型分级；协议明写「挂牌≠可采购」 |
| 媒体转述被升格为行政许可 | 二手报道读起来像一手 | 每条结论标注证据类型；引用不得升格写进协议 |
| 已排除的旧口径仍占据核心论点 | 数字被推翻后，引用它的论证骨架不会自动消失 | 全库残留扫描；旧口径须显式退役或降级为情景 |
| 区间其实是两个基数的拼接（「78–81%」） | 区间由多组数据拼出，读者以为同源 | 口径必须逐条登记；跨口径不得合并 |

### B. 写作层

| 症状 | 为什么会发生 | 防线 |
|---|---|---|
| 臆测数字伪装成「前轮内部测算」 | 自己扩展的假设经一次自我引用就变成「依据」 | 元叙述扫描 ＋ 溯源（grep 历史材料，零命中即判定为臆测） |
| 元叙述（「如前所述」「本报告下一阶段」） | 写作过程的痕迹没清 | 确定性词表扫描（`forbidden_terms.json`） |
| 自述型表述（「本报告不给出…」） | 用写作姿态代替结论 | 同上；口径/方法声明类刻意保留，故需白名单 |
| AI 腔（「第一性原理」「赋能」「抓手」「闭环」） | 套话模板 | 词表拦截；注意「闭环」误报率高，需谨慎选择或白名单保护 |
| 白名单被整行豁免 → 绕过 | 白名单按「行」匹配，同行既有违规又有严谨声明就整行放过 | 白名单改**句粒度**判定 |
| 严谨性声明被误杀 | 扫描器不懂「本报告不构成法律意见」是合法的 | 9 类严谨性声明白名单，且必须**零误报**进验收 |

### C. 交付工程层

| 症状 | 为什么会发生 | 防线 |
|---|---|---|
| 目录页码与正文对不上 | 目录用「页码占位 + 固定偏移」回填 | 按正文实际出现位置定位；**生成侧与校验侧各自独立实现**，不共享偏移常量 |
| 校验器检不出自己的 bug | 校验复用了生成侧的同一个错误假设 | 校验与生成禁止共享页码推算逻辑；反向验证（人为改错必须被抓出） |
| 目录行溢出 | 制表位宽度 > 正文文本宽度 | 制表位由页宽与边距算出（A4 11906 − 1440×2 = 9026 twip） |
| 表格塌成一列 | 生成器引用了未定义的段落样式 | 生成器直写 OOXML，不走 Markdown/HTML 转换链 |
| 整包哈希不同就判内容变了 | zip 条目时间戳进了哈希 | 比对到**部件级**哈希 |
| PDF 生不出来却报成功 | soffice 缺失被静默吞掉 | 降级必须显式标记（`pdf:false`），调用方须解析 JSON 而非只看退出码 |
| 构建不确定 | 构建器写入随机/时间戳内容 | 同一输入连续构建两次，部件哈希必须逐项一致 |

### D. 流程与协作层

| 症状 | 为什么会发生 | 防线 |
|---|---|---|
| 接手时把旧项目的「已核验／A级」当既成事实 | 标签随文件一起被继承 | 继承声明逐条 `human_decision`（CONFIRMED/REVISED），未决不得入正文 |
| 导航与进度状态失真 | 没人负责把状态写回入口文件 | 唯一进度总控＋同步台账；状态四分不得互相替代 |
| `revision` 变了但正文没变 | 平台版本号不等于内容变更 | 以全文 diff 为准，不以 revision 为准 |
| 用户手改被覆盖 | agent 不知道线上被改过 | 写前读最新版本；发现手改即停并报告 |
| 机器自己签掉人审门 | 只检查了 `agent:` 前缀这种窄写法 | 机器标记词表（含中文）＋ 桩件拒绝 |
| 测试把仓库跑脏 | README 里的命令直接改随库夹具 | 会写盘的命令必须先复制到临时目录；夹具复原步骤写进 README |
| 变更后非目标区域被顺手改了 | 局部改写没有边界校验 | 零漂移比对：未声明区域字符级差异必须为 0 |
| 建议澄清项被做成硬门禁 | 把「有助澄清对象的清单」当成「准入条件」 | 八项各登记 `clarification_status`，未澄清按默认行为执行且不阻断 |

## 三、几个刻意的取舍

**为什么澄清项不设硬必填**：填不出来硬填会制造假答案，比不填更糟。设计上改为「未澄清 → 登记状态与原因 → 按协议默认行为执行 → 不阻断」，只保留一条条件性要求：**确实存在在线文档时，「以哪个为准」必须由人明确**（否则无法决定写哪）。

**为什么反对 pandoc 直出 docx**：转换链会引入未定义样式（表格塌成一列的根因），且很难逐项控制版式。改为单源 markdown 直接写 OOXML。

**为什么复核必须异族**：LLM-as-judge 有确证的 self-enhancement 偏差——模型偏爱自家输出。用同族模型互审等于让偏差自证。

**为什么校验器不能复用生成器的逻辑**：生成器与校验器共享同一个错误假设时，校验会为错误背书（本项目真实踩过：目录页码偏移错误同时存在于两侧，校验「全绿」）。

**为什么变更走 delta 而不是直接改**：主规格是收敛态事实源，改动必须留增量、留归档、可回溯。OpenSpec 的实测限制也已记录在协议里：归档忽略 `## Purpose`、不支持 Scenario 级改名。

## 五、怎么扩展

1. **换议题不换骨架**：P1 的八项是通用清单，P3 的 `task.json` 与 P4 的底表随议题变化，骨架与门禁不变。
2. **加新校验**：先写判据与执行体的追溯关系（脚本 CLI + 退出码 + stdout JSON），再写实现；每条新规则必须配一条**阴性对照**（用含已知缺陷的旧料喂新校验，必须报错）。
3. **加新边界**：在 `review_loop_engine.md` 增一节边界特化，并同步在追溯矩阵与规格里登记。
4. **接在线平台**：写一个满足 `storage_adapters.md` 契约的 Adapter，声明 `source_of_truth` 分支即可，不改主流程。
